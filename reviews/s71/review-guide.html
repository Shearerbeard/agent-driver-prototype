The 80/20 review order

Heaviest first. Each item says what to open and what would make it wrong.

1The terminal mechanism heaviest

The pinned substrate has no terminal-tool concept: nothing a tool returns can end the loop. So respond records the answer into a first-write-wins slot and the loop ends the two ways the substrate ends it — the model stops calling tools, or LoopBudget (mapped to max_tool_depth) fires. A consequence the codex panel leg forced into the open: the substrate refuses the exhausting response's tool calls without executing them, so S39's post-exhaustion terminal opportunity is dropped — a budget-stopped run gets the host-authored fallback, never one last model-authored answer.

Open: src/coordinator_loop/outcome.rs (the total stop-reason × slot join), DESIGN.md "What the loop is" and section 5.

Wrong if: you want the S39 exhaustion-turn semantics preserved in the spike, or you read the card's LoopBudget requirement as demanding a host-side counter rather than the substrate's own depth cap.

Per your direction at this gate, the tested depth is now encoded: LoopBudget::CANONICAL = 12, derived from the canonical config's max_planning_cycles = 4 (a cycle is a create_plan+execute pair, one turn writes the answer, three cover inspect_run slack), pinned by a unit test — instead of leaning on the substrate's default of 25.

2Acceptance test 1: no stream break heavy

tests/coordinator_loop.rs::create_plan_then_execute_continues_without_a_stream_break — three tool rounds (create_plan, execute, respond) inside one AgentLoop::run, tool order asserted by observer, plan in the store under a precomputed deterministic id, stub execution recorded, answer committed. The mock panics on queue exhaustion, so the call arithmetic (4 queued responses, 4 provider calls) is proven by the test passing at all. This is the behavior aura's bounded router cannot produce: its stream breaks the moment a routing tool writes.

Wrong if: the assertions don't convince you the loop truly continued through planning and execution in one conversation.

3Acceptance test 2: budget-forced termination medium

turn_budget_stops_the_loop_and_the_host_writes_the_answer — budget 2, third response's tool call refused before dispatch (observer proves exactly two ToolCallStarts), outcome is BudgetExhausted with the host fallback rendered from the stub execution's evidence through the ported frame renderers. A sibling test proves the no-execution fallback template lists the unexecuted plan.

The card requires the opening message to render through the S70-ported planning_prompt.md — and it does, byte-faithful. But that template tells the model to call one of the bounded router's three tools EXACTLY ONCE, while this loop registers four different tools. Recorded as DESIGN.md R1: S72 must port a loop-shaped planning template before any benchmark read is meaningful. MockProvider tests are unaffected (the mock never reads prompts).

Wrong if: you consider the mismatch disqualifying now rather than an S72 duty.
